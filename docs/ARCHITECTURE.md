# 架构和原生边界

## v0.3.2 统一路由

桌面应用和 `server.py` 默认启动三个后端。`bridge_config.py` 定义 model 路由及初始并发配置，`bridge_pool.py` 为每个后端持有独立的准入信号量、线程预算与占用名额。每池默认 4 路，各池按配置值独立运行与排队。占用格子统计已取得本池额度的请求；取消排队会清理等待计数。健康检查中的汇总容量为各池配置之和，仅用于描述，调度只使用各池各自的信号量。只接受三个正式 model 名称，model 必填。

`WechatBackend` 复用微信进程级 agent，并为每次识别维护独立会话。`WetypeBackend` 复用输入法 agent，但每条音频独立编码、独立 voice_id、独立回调所有权；完成清理只检查当前所有者。`DoubaoBackend` 为每个请求正常初始化新游客会话，通过内存中的 PCM 数据转写，不读取浏览器登录资料，也不持久保存上传音频。

`/health` 返回每个池的容量、占用索引、排队数及最近错误。状态检查不会创建原生钩子或匿名语音请求，不能证明上游当前可用性。`desktop_ui.py` 只负责浅色双页界面和格子绘制，服务所有权、鉴权与正常退出逻辑保留在桌面生命周期层。`docs/api.html` 是独立的离线文档，也通过 `/docs` 提供。

以下内容描述微信桌面端的专项原生路径；图中的 4 路是旧版默认值，v0.3.0 已改为配置值。

```text
OpenAI SDK / HTTP 客户端
          |
          | multipart POST /v1/audio/transcriptions
          v
FastAPI（本机监听、输入验证、4 路并发准入，超出排队）
          |
          v
音频解码为 16 kHz / mono / PCM16
          |
          v
Frida 元数据读取 -> 已加载 DLL 指纹对比（不匹配只警告，继续尝试）
          |
          v
微信进程内 agent.js
  原生编码器 -> 自建 iLink 会话 -> 现有登录和网络层
          |
          v
微信语音识别服务 -> 响应回调 -> 最终 UTF-8 文本
          |
          v
取消并析构自建语音会话 -> 保留进程级 agent -> HTTP 响应
```

网络发送和析构在微信已有的有效协程上下文中执行，不能直接从 Frida 工作线程调用。这一条件来自运行时异常与反汇编的交叉验证。

`agent.js` 中的 RVA、虚表和对象布局仅对应已核验的 4.1.13.65 DLL。构造回调、原生字符串对齐分配与释放、异步响应保护和析构必须一起适配；不能只替换几个地址。

同一个微信进程复用一个 Frida session 和 agent。Python 只在创建、替换和关闭 agent 时保护共享状态，识别 RPC 在锁外运行。每个请求使用独立会话 ID、原生对象、事件和缓冲区；回调按照原生对象指针路由到所属请求。协程任务进入 FIFO 队列，创建、提交和析构动作依次获得有效协程上下文，但等待网络响应的识别会话可以同时在途。超时的队列项只删除自己的任务。

每次请求仍会取消并析构自己的原生语音会话，但不会逐请求卸载脚本。`finalize(request_id)` 只清理该请求，重复清理复用同一个 Promise，避免重复析构。先在协程中调用已核验 iLink strategy 的停止函数，注销网络回调，再等待取消标志的 shared_ptr 强引用数降到 1（strategy 自身所有权），并在实际析构前再次检查。30 秒内不能释放在途任务所有权时保留对象并暂停调用，不能用固定延时替代退出条件。协程 hook 执行动作期间禁止嵌套分派下一项任务，防止原生调用重入时提前执行其他请求的析构。

自建对象的虚表指向进程持有的三个 x64 原生空函数，不再存放 `NativeCallback` 地址；结果和错误通过这些入口上的 Interceptor 读取，处于清理阶段或未知对象的事件被忽略。空函数由 VirtualAlloc 分配、写入后改为只读可执行，回调虚表使用微信 allocator；每次 agent 连接保留一页 4 KiB 及 64 字节虚表直到微信进程退出。这个小额资源保留是有意的：脚本正常卸载或宿主意外退出后，Frida 移除 hook，原生回调地址仍有效。它不代替原生对象所有权检查，也不能证明其他内存破坏路径不存在。请求结束后仅释放自己的临时缓冲区引用，避免清理一个请求时影响另一个请求。

服务停止时停止新请求准入，等待全部在途请求及各自的清理完成，再显式分离四个 Interceptor 钩子、卸载脚本并分离 Frida session。若原生析构状态不确定，则暂停后续请求并保留 agent；停止操作也会等待微信退出。断连回调记录原因，不阻塞 Frida 的信号线程；意外断连不能被当作微信已退出，同一 PID 被暂停调用，避免向清理状态未知的进程重新注入。确认微信进程终止或发现新的主进程后可以恢复连接。

2026-10-14 的两次 Windows 崩溃转储均记录 `frida-agent.dll` 的 `0xc0000005`，读取地址为 `0x18`。第二次的故障指令与 Frida 17.23.3 的监听器入口分发实现一致：入口收到空监听器对象。逐请求注入、分离与钩子对象生命周期是据此排查和修复的重点，但转储不能单独证明是哪一次释放导致对象失效。改用常驻 agent 是针对该触发路径的修复，有限的复验不能证明所有失败路径或长期运行都安全。

当天 21:33 的微信自有小型转储另外记录执行访问违规：虚函数调用跳到不可执行的私有堆内存，崩溃时 Frida 已卸载，服务日志缺少正常关闭记录。原生任务退出检查、重入保护及独立于脚本的回调入口针对这类生命周期风险；小型转储未保存涉事对象，不能据此断言已定位最初的覆盖/释放位置。独立子进程测试可在正常卸载和强制结束测试宿主后确认 Frida DLL 已卸载、原生入口仍可调用；这不等于在真实微信上完成了意外退出后的长期安全验证。

`/health` 的 `agent_connected` 与 `agent_generation` 用于确认连接是否仍有效、连续请求是否复用同一个 agent；`active_requests`、`queued_requests` 和 `max_concurrency` 显示 HTTP 占用槽位、排队请求及并发上限。已连接的 agent 复用已验证的进程身份，不因当前窗口从聊天变为“图片和视频”而重新按标题查找进程。新连接选择具有窗口且响应正常的微信进程；存在多个候选时仍要求指定 PID。`last_success` 仍是历史成功时间，不能据此判断当前微信登录状态。运行日志记录 attach、close 和请求完成的时间、PID 与 generation，不记录转写文本。

`server_response` 日志中 `seq` 是旧标签，读取的是对象 `+0x04` 的原始整数，完整业务语义未恢复；它不是公开保证的网络序号。API 只返回已验证的最终 `text`，不伪造时间戳、置信度或模型使用量。

默认不会保存上传音频和转写文本。合成测试语音、API 兼容测试与本机运行记录分开：公开仓库只保留源码和合成 fixtures，运行报告、日志、PID、环境和密钥配置均被 Git 忽略。
